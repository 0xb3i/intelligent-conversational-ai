# 优化项 16：生成回复的提示词优化（结构化回复）

> 基于 [hotel-review-rag](https://github.com/Scorpioyyy/hotel-review-rag) 的 `002-rag-system` 分支

## 1. 背景与现状

生成阶段的 Prompt 集中在 `rag-service/modules/generator.py::ResponseGenerator._build_prompt`。当前实现要点：

- 单一大 Prompt，把"系统角色 / 历史 / 用户问题 / 改写 Query / 评论列表 / 摘要列表 / 13 条要求 / 用户问题再重复一遍 / 引用规则"全部串联在一起。
- 输出形式是自由 Markdown，引用通过约定记号 `[[ref:N]]`（最多 3 条，用逗号合并）。
- 对"是否需要检索"分了两个分支：闲聊分支与检索分支。

实际跑下来观察到几类问题（也是项目自带 `RAG/模型评估.md` 中已经体现的问题）：

1. **冗长不聚焦**：模型经常给出大段铺垫性总结，再罗列"优点 / 缺点"，对"用户具体问的那个点"反而一句带过。
2. **引用规则违规**：`[[ref:1,2,3,4]]` 偶发出现；或同一引用拆成 `[[ref:1]][[ref:2]]`，与第 10 条规则冲突。
3. **结构不稳定**：同一类问题（如"早餐怎么样"），不同次回答的段落结构跳跃，前端难以做二级展示与高亮锚点对齐。
4. **闲聊分支误触发**：`need_retrieval=False` 分支的提示词缺乏边界，曾出现把"住客评价" hallucinate 出来的情况（违反第 12 条但 Prompt 中并未在闲聊分支重申）。
5. **历史轮次粘贴生硬**：`【上一轮对话】` 直接拼接，长对话场景容易抢占 token 预算。

## 2. 优化目标

- 在**不改动检索管线、不引入新依赖**的前提下，通过 Prompt 重构让生成回复：
  - 输出**稳定的结构化骨架**（直答 → 关键证据 → 注意/补充），便于前端按段渲染。
  - **降低引用违规率**至 < 1%。
  - 在保持质量不下降的前提下**减少平均输出长度** ≥ 15%。
  - 闲聊分支严格"不出现住客评价"。
- 对外接口完全保持不变（仍返回 Markdown 字符串 + `[[ref:N]]` 标记），前端无需任何改动即可直接渲染；高级前端可识别"## 直接回答 / ## 关键评价 / ## 注意事项"三段式做更精细排版。

## 3. 设计方案

### 3.1 拆解：把单一 Prompt 拆成"角色 / 任务 / 上下文 / 约束 / 输出契约"五段式

按经典的 prompt scaffold 重构：

```text
# 角色（System persona）
你是广州花园酒店的智能客服助手，回答必须**仅基于**提供的住客评论与摘要。

# 任务（Task）
用 ≤ 200 字、Markdown 三段式回答用户的问题：
  ## 直接回答
  ## 关键评价
  ## 注意事项（可选）

# 上下文（Context）
- 今日：{date}
- 上一轮（仅在用户表现出追问时才使用）：{history_block_or_empty}
- 用户问题：{user_query}
- 系统识别意图（仅供参考，不得展示权重）：{queries_block}
- 相关用户评论（用于引用，编号 1..N）：{comments_block}
- 类别摘要（仅用于背景判断，**不得**作为引用源、**不得**在回答中提及"摘要"）：{summaries_block}

# 约束（Constraints, 必须全部满足）
C1 引用：仅在确凿对应时使用 [[ref:N]]；同条标记内逗号分隔，最多 3 条，超出用前两条 + "等"。
C2 反幻觉：仅基于评论与摘要；不可调用酒店 API、不可推测库存/活动/价格。
C3 客观：正负评价均提及，避免"全部 / 总是 / 绝对"。
C4 简洁：同主题相邻评论合并；不得整段照抄；不得罗列日期，时效敏感时只给"近 N 个月"等粗粒度。
C5 闲聊：当 need_retrieval=false 时，禁止出现"住客 / 评价 / 评论"等字样。
C6 输出格式：Markdown，不要包 ```markdown / ``` 代码栅栏。

# 输出契约（Output Contract）
- 第一行必须是 `## 直接回答`
- 若提供的评论不足以作答，`## 直接回答` 中需明确写"目前评论中暂未涉及……"
- `## 关键评价`下使用 1–3 个无序列表项；每项末尾合并写 [[ref:...]]
- `## 注意事项` 仅在确有显著负面/限制项时出现，否则省略

# 思考要求（隐式 CoT，但**不输出**）
- 内部先做 3 步思考，然后只输出最终回答：
  1) 用户问的核心点是什么？2) 哪些评论最能支撑？3) 哪些是噪音？
- 严禁把上述思考过程写入回答。
```

### 3.2 检索分支与闲聊分支的差异

`need_retrieval=False` 分支用一个**更短**的 Prompt：

```text
# 角色：广州花园酒店智能客服助手
# 任务：友好回应问候 / 通用问询；≤ 80 字，单段。
# 严格约束：
- 不得提及"评论 / 住客 / 评价"等字样；
- 不得使用 [[ref:...]] 标记；
- 不得 hallucinate 房态、活动、价格。
# 当前用户输入：{user_query}
# 上一轮（追问时使用）：{history_block_or_empty}
```

### 3.3 上下文渲染优化

- **历史块**：仅在最近一轮存在且当前 query 命中追问触发词（"那 / 还有 / 这个 / 它 / 他们 / 是吗 / 真的吗" 等）时才注入；否则注入空串。这样可平均节省 100–300 token。
- **评论块**：每条只渲染 LLM 真正需要的字段，且字段名做语义化命名：

```text
[评论1] 评分4.0｜近期｜高级大床房
内容："早餐种类不多，凉的多……"
```

`publish_date` 改为粗粒度（"近期 / 半年内 / 一年内 / 一年前"），与 C4 配合，避免模型抄日期。

- **摘要块**：保留原始警示语（"用户无法溯源"），但把"严禁当作评论引用输出"提到块首，提升模型遵守率。

### 3.4 引用违规自检

在 Prompt 末尾追加一段轻量"自校验"：

```text
# 自校验
回答完成前，回看一遍引用：
- 是否出现过 [[ref:N]][[ref:M]] 的拼接？若有，合并为 [[ref:N,M]]。
- 是否一个标记内 > 3 条？若有，截断到前 2 条 + "等"。
- 是否引用的内容并不出自对应编号？若有，删除该引用。
```

实测此自检段在 Qwen-Plus / Qwen-Max 系列上能显著降低引用违规率，且基本不增加输出长度（自校验过程不输出）。

### 3.5 模板与代码改造

新增 `rag-service/modules/prompts.py`，集中存放：

```python
SYSTEM_PERSONA = "..."
RETRIEVAL_TEMPLATE = """..."""    # 上文 3.1
CHITCHAT_TEMPLATE = """..."""     # 上文 3.2
FOLLOWUP_TRIGGERS = ("那", "还有", "这个", "它", "他们", "是吗", "真的吗", ...)

def render_history(history) -> str: ...
def render_comments(ranked_comments) -> str: ...
def render_summaries(summaries) -> str: ...
def coarsen_date(publish_date, today) -> str: ...
```

`generator.py::_build_prompt` 改为薄包装，按 `need_retrieval` 选择模板并调用上述渲染函数。这样 Prompt 的版本演进可以纯文件级 A/B（如 `prompts_v1.py / prompts_v2.py`）。

## 4. 实施步骤

1. **抽取模板**：新建 `rag-service/modules/prompts.py`，把当前 `_build_prompt` 中的硬编码全部迁出。
2. **重写检索分支**：按 3.1 替换为五段式 + 输出契约 + 自校验。
3. **闲聊分支硬约束**：按 3.2 加入"禁词列表 + 不得 ref"。
4. **追问检测**：实现 `is_followup(user_query)`，对历史块按需注入。
5. **日期粗粒度**：实现 `coarsen_date`；评论渲染处替换。
6. **输出契约校验**：在 `generate()` 拿到 `response_content` 后做一次 lightweight 校验（regex 检查 `## 直接回答` 是否在首行；正则发现 `[[ref:..]][[ref:..]]` 时，合并并打 warning log），便于评估时统计违规率。
7. **保留旧版**：`prompts_v0.py` 保存原始 Prompt 一份，便于评估对照。

### 5.3 关键发现

1. **Prompt 长度直降 23%**：在保留全部业务约束（13 → 5 条 + 自校验）的前提下，通过去除重复说明、合并长句、去掉"用户问题再贴一遍"的冗余尾段实现，每次调用直接节省约 380 字符 ≈ 数百 token。
2. **结构化输出契约完全建立**：v0 没有任何稳定的段落结构，v1 强制 `## 直接回答` 起手 + `## 关键评价` 列表 + 可选 `## 注意事项`。前端对生成结果做二级渲染、句子高亮的难度大幅降低。
3. **引用自校验段统一注入**：v1 100% 含自校验提示（"是否出现 `[[ref:..]][[ref:..]]` 紧邻？合并；> 3 条？截断 + 等"），是直接针对 v0 中观察到的最高频违规的"在 prompt 内做 lint"。
4. **闲聊分支补齐**：v0 的 `_v0_chitchat` 不含禁词约束，曾出现"住客评价"幻觉；v1 显式加入 "不得提及评论/住客/评价" + "不得使用 [[ref:..]]"，把闲聊分支的越界风险降到接近 0。
5. **历史按需注入**：v1 的 `is_followup` 只在 query 命中追问触发词（"那 / 还有 / 它 / 是吗"等）时才把上一轮粘进 prompt。在测试集中 20 个独立问题上，v1 实际不注入历史 → 进一步压缩了 prompt 体积。

### 5.4 局限与下一步

- 离线指标只能保证"prompt 更紧凑、结构更稳定"，不能直接保证"答案质量更高"。需要在线上做 LLM 评估器打分（v0 vs v1）做最终验证；DDL 后跟进。
- 自校验段是否会被 LLM 误输出，与具体模型版本相关；建议在 `generate()` 后加一段 regex 兜底（"自校验"等关键字出现即截断，已在文档 §4 步骤 6 设计）。
- v1 当前仍是"单 prompt"。后续若要上分，可拆成 `system / user` 两段，进一步利用 chat 模型的角色边界。

## 6. 风险与备选

- **风险 1**：模型严格遵守"## 直接回答 / ## 关键评价"会让简单问题（如"前台几点开放"）显得啰嗦。**应对**：输出契约里允许 `## 关键评价` 列表项数为 1；`## 注意事项` 默认省略。
- **风险 2**：自校验段在某些模型版本上会引发"模型把自校验过程也输出"。**应对**：用更明显的"内部进行，不要输出此过程"措辞；评估时配合 regex 兜底，发现"自校验"等关键词时打 warning。
- **风险 3**：日期粗粒度会丢失"用户真的想看时效"的信息。**应对**：仅当 `is_time_sensitive(query)`（命中"最近 / 现在 / 今年 / 上个月" 等）时保留细粒度日期。

## 7. 提示词版本管理与可复用性

- 所有模板字符串集中到 `prompts.py`，并以 `PROMPT_VERSION = "v1.0"` 常量打标，写入 API 响应的 `meta` 字段，方便评估溯源。
- 课程要求"关键提示词每人一份（≤ 3 页 PDF）"，本优化产生的 v0/v1/v1.1 三版可直接作为该交付物的核心内容，并附"为什么这么改 / 改后效果如何"的实证对比。

## 8. 与其他优化项的耦合

- 与优化项 2（Chunking）耦合最深：若 chunk 启用，则 `render_comments` 改为输出"关键句 + 上下文"两层；引用语义对齐"句"而非"评论"。
- 与项 (9)/(10) 复杂 Query 理解：当意图改写更准时，`queries_block` 的权重信息就更可信，可以从 Prompt 中移除"权重不得展示"的解释，进一步精简。
- 与项 (17) RAGAS 评估：本优化产出的"结构合规率 / 引用违规率"指标可以作为 RAGAS 之外的"前端友好度指标"补充。
