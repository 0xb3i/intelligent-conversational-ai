# 关键提示词（本轮增量）—— 我对 AI 助手的指导过程

> 本文件记录我在推进**类目摘要 v2** 与 **BM25 倒排索引 v2** 这两项优化时，对 AI 编程助手输入的关键提示词。区别于运行时给 LLM 用的 prompt，这里收录的是「我作为开发者，怎样把模糊的工程目标拆解、对齐、推进到落地」的对话脉络。重点不在指令本身，而在每条指令背后的**判断与取舍**。
>
> 原 `关键提示词.md` 不动，本文档作为增量补充；正文按时间顺序分两条链路叙述。

---

## 链路一：类目摘要 v2 + 两阶段摘要检索

### 起点观察：我先描述病灶，而不是直接给方案

最初我并没有立刻让 AI 去改代码，而是先把症状摆出来，让它跟我一起判断病根在哪：

> **Prompt #1**
>
> 「目前每个类目只有一段 600 字左右的长摘要，是把整类评论一次性丢给 LLM 写出来的。我观察到两个问题：① 用户问『有什么投诉』时，回答里仍然会出现『但服务整体还是不错的』这种折中表述，因为摘要里正负观点混在同一段；② 模型对哪些问题是『高频反复出现』、哪些是『偶发抱怨』完全没有区分，回答里它们的权重一样。请先告诉我，这两个症状的根因在『摘要的内容』还是『摘要的结构』，**不要先动代码**。」

> **思考动机**：工程优化最容易踩的坑是「先动手再想」。我特意加了「不要先动代码」，是因为如果根因在结构而不是内容，那改 prompt 调摘要文案没用，必须把数据 schema 改了。让 AI 先做归因再出方案，可以避免我和它一起在错误的方向上累积工作量。

AI 回应「根因在结构」之后，我才进入下一步。

### 方案对齐：我用边界条件驱动设计，而不是堆功能

> **Prompt #2**
>
> 「方案我同意是结构问题。但在你提具体 schema 之前，先帮我把**边界条件**列清楚，再回头设计：
>
> 1. 一个类目下，正负面观点的数量可能差距很大（如『卫生』可能是 8 正 2 负，『噪音』可能是 1 正 9 负），结构必须能反映这种不对称
> 2. 同一个 subtopic（如『早餐』）很可能同时存在正面和负面要点，结构里要允许它们并存而不是被强行合并
> 3. 用户问题的极性是动态的（亮点/投诉/中立），后续检索要能按极性过滤，所以极性必须是**结构化字段**而不是混在 summary 文本里
> 4. 一次 LLM 调用塞几百条评论会触发长文本退化、JSON 不稳定，生成端要能切块
>
> 基于这 4 条，再给我 schema 和生成流程。」

> **思考动机**：第 1、2 条是我读评论数据时自己观察到的特点；第 3 条是我从「这个摘要要给检索用，不仅是给前端展示用」这个出发点反推出来的——只有把极性结构化，下游意图检测才能精确过滤；第 4 条是我对长文本任务的工程经验。把这 4 条边界条件提前列死，AI 给出的 schema 才不会只覆盖「显然该有的字段」。

AI 据此提出 `overview + points[]` 的双层结构、Map–Reduce 流水线、以及每条 point 的 `subtopic / polarity / summary / keywords / salience` 字段后，我才同意它进入实现。

### 实现阶段：我把「Map 与 Reduce 的职责」分得很死

> **Prompt #3**
>
> 「写 Map 阶段的 prompt 时，我有几条硬约束：
>
> - Map 的产物必须是『**候选要点的并集**』，不允许它去重、不允许它合并、不允许它排序——这些是 Reduce 的职责，让 Map 干 Reduce 的事会导致全局信息缺失下做的合并是错的
> - 每条候选要点都要带 `mentions`（在本块内的提及次数估计），这是 Reduce 阶段做显著度加权的输入，不是 Map 自己的产出
> - Map 不允许丢弃极性为 neutral 的要点，全部交给 Reduce 决定
> - 同一 subtopic 下的正负要拆成两条，**绝不**合并成一条带『有人觉得好有人觉得不好』的中性要点
>
> Reduce 阶段反过来：
>
> - Reduce 的输入是『所有 Map 块的候选要点的并集』，不再看原始评论——这是为了控制 Reduce 的上下文长度，让它在结构化数据上工作而不是再读一遍文本
> - Reduce 必须给出 salience（0–1 浮点），且分布要拉开，不允许全部 0.9 这种偷懒输出
> - overview 必须 2–4 句、且**必须同时反映优点与不足**（如果该类目两面都有的话），这是为了让 overview 在第一阶段召回时不会只命中一种极性的查询
>
> 你按这个职责切分写 prompt，不要混用。」

> **思考动机**：Map–Reduce 在分布式计算里之所以稳，是因为 Map 与 Reduce 的职责严格分离。LLM 流水线很容易反过来——让 Map 自己「顺手」做点合并、让 Reduce 自己「顺手」回看一下原文，结果两边都不可控。我把职责钉死，等于让两个 prompt 各自只解一个良态子问题。

### 检索接入：我反复确认「召回粒度」与「展示粒度」

> **Prompt #4**
>
> 「v2 摘要的检索我要明确分成两阶段：
>
> 1. **第一阶段**在 overview（14 条）上召回，目的是**定位类目**——overview 是『这个类目下大致是什么情况』的浓缩，召回粒度对应『用户问的是哪个大主题』
> 2. **第二阶段**在 points（84 条）上召回，但召回范围**限定在第一阶段命中的类目下**——points 粒度太细，全局召回会让用户问『早餐』时把『卫生间布局』之类完全无关的 point 拉进来
>
> 极性过滤只发生在第二阶段。意图检测的 `expected_polarity` 字段不参与第一阶段召回，因为 overview 必须双极并存，否则第一阶段会丢掉对端的类目。
>
> 命中的 points 进入回答 Prompt 时，**作为答案骨架而非引用源**——这点很重要，回答里**不能**出现 `[[ref:N]]` 指向 point，引用必须只指向原始评论。否则用户点引用想看证据时会跳到一段已经『二次加工过』的文字，证据链断了。」

> **思考动机**：「召回粒度」和「展示粒度」是两件事，新手很容易合并处理。我把它拆开是因为：overview 在召回阶段是**索引**（用来定位），但在拼答案时它已经太冗长不该用；points 在召回阶段是**精排目标**，在拼答案时用作骨架但不能当引用源；真正能当引用源的只有最原始的评论。这个三层关系如果不在指令里说死，AI 很容易把 points 直接当成引用挂出去——那用户点开就是一段总结而不是评论原文，整个 RAG 的可验证性就被破坏了。

### 意图检测改造：我只让它加一个字段，不让它重写

> **Prompt #5**
>
> 「意图检测里我只新增一个字段 `expected_polarity`，**不**改房型识别和时效性识别的现有逻辑。给 LLM 的判定标准我列三档（positive / negative / [positive, negative]），加一个 None 档兜底。每档都给 2–3 个例子，例子要选**容易混淆**的（比如『值得住吗』要标 positive、『差不差』要标 negative，不要给『推荐什么』『投诉什么』这种过于明显的）。
>
> 而且——只看用户问题的字面与语气来判极性，**不要让模型尝试推断回答内容**。这是为了避免它在意图检测阶段就开始『预演回答』，把判断染色。」

> **思考动机**：往一个已经稳定运行的检测器里加字段，最大风险是顺手把已有判定逻辑改坏。「不动其它字段」是硬约束。例子选「容易混淆」是因为简单例子模型本来就会判对，给它简单例子等于浪费 prompt 长度且无法提升边界判别能力。最后那句「不要预演回答」是我从过去观察到的现象总结的——LLM 一旦开始想答案，意图判断就会被带偏。

### 回答 Prompt 的兜底：v1 不删

> **Prompt #6**
>
> 「v2 摘要渲染分支接入回答 Prompt 时，**保留 v1 整段摘要的渲染分支**，按 `schema_version` 字段路由。理由：① 万一 v2 入库失败，链路要能自动降级；② 离线对照评测时，v1 与 v2 要能在同一份运行时代码里来回切换。
>
> 这个不是临时兼容，是长期保留的设计。」

> **思考动机**：上线一个新结构的同时把旧结构的代码路径删掉，是工程上一个常见的不可逆错误。保留 v1 分支几乎不增加维护成本（就是一个 if 分支），但能给我留出『对比、回退、A/B』三种灵活性。

## 链路二：BM25 倒排索引 v2

### 诊断阶段：我让 AI 先去看证据

> **Prompt #7**
>
> 「现在 BM25 路在短 query 上召回质量明显不行——我观察到『早餐怎么样』这种问题，BM25 召回的 Top10 里有一大半评论根本没出现『早餐』这个词，而向量路反而能召回。但这不该啊，BM25 应该是字面匹配最强的那一路。
>
> 你**先不要改代码**，先去看：
>
> 1. 现有 `tokenize` 函数对几个酒店常见复合词（早餐厅 / 行政房 / 自助晚餐 / 500 元 / 2 人间）实际切出来是什么 token
> 2. 现有索引词表里有没有『早膳 / 早点 / 早饭』这些与『早餐』同义的词项，以及它们的 doc 数大致是多少
> 3. 跟我汇报你看到的具体证据，我们再判断病根在分词、在词项匹配、还是在两者都有」

> **思考动机**：我有怀疑（jieba 默认词典 + 字面匹配局限），但我不让 AI 直接照我的怀疑去改——这是工程上很容易犯的「假设驱动开发」。让它先验证证据，可以排除「问题其实是别的，比如索引根本没建对」这种我没想到的可能性。结果它跑完之后回来告诉我「分词把『早餐厅』切成两个 token，且数字被正则吃掉了」「同义词项确实存在但 BM25 不会跨字面匹配」——两个原因都成立，方案才落地为「词典 + 同义词扩展」双管齐下。

### 方案约束：我用「不可改动什么」来限定空间

> **Prompt #8**
>
> 「方向同意。但在你写代码前，把**不可改动的边界**列清楚：
>
> 1. **BM25 公式不动**：k1、b 可调，但不允许换成 BM25+、BM25L 之类的变体——下游评测脚本是按经典 BM25 算的，换公式会让所有历史指标失去可比性
> 2. **索引文件协议不动**：`inverted_index_chunked.pkl` 的字段结构必须保持向后兼容，因为离线 build 与在线 search 是同一份文件，且其它同事可能在用
> 3. **同义词扩展只能在查询侧做，不能在索引侧做**：如果在索引侧把『早膳』也写进『早餐』的倒排表，词典一改就要全量重建索引，且会污染 IDF 统计；查询侧扩展则可以热改、不重建
> 4. **数字保留默认开但留开关**：万一某些场景（比如纯中文查询）数字会引入噪声，要能一键关掉
>
> 满足这 4 条之后，方案空间剩多少你都可以选。」

> **思考动机**：列「不可改动什么」比列「应该做什么」更有效——后者是开放命题、容易被无限延展，前者是闭包问题、能精确切出方案空间。第 3 条是关键的设计选择：索引侧 vs 查询侧扩展是两种思路，我倾向查询侧的核心理由就是「热改 + 不污染 IDF」，这点我必须前置说清楚，不然 AI 可能两边都做或挑错边。

### 配置集中化：我顺便要求做一件「看起来无关」的事

> **Prompt #9**
>
> 「这次顺带把所有 BM25 相关的可调参数（k1 / b / 词典路径 / 同义词路径 / 数字开关 / 扩展开关）**全部集中到 `config.py`**。理由：
>
> - 离线 build 脚本和在线 search 模块如果各自硬编码参数，迟早会失同步——评测时跑出来的指标对应的参数和线上跑的不是同一组，结论就废了
> - 后续做 A/B 调参或灰度时，只改一个文件就能切；不集中的话每次都要全局搜索改 N 处
> - 这件事**必须和这次改造一起做**，否则等参数已经散落各处再回来集中，工作量翻倍且容易漏」

> **思考动机**：「顺带做」的事最容易被推迟，但配置集中化是那种「越早做越省、越晚做越亏」的债。我把它和主任务捆在一起，是因为这次本来就要新增至少 4 个参数（词典路径、同义词路径、两个开关），不集中就会立刻产生 4 处散落点；现在做边际成本最低。

### 评测设计：先想指标，再写脚本

> **Prompt #10**
>
> 「写评测脚本之前，先把指标设计讲清楚：
>
> - **soft_recall@10** 是主指标。我们没有逐条 query 的 ground-truth 文档，但有 query 的 `intent_direction` 标签——按这个标签反查类目的关键词集合，TopK 里只要有一条评论命中关键词就算对。这个『软』是我接受的精度让步，但优于完全没指标
> - **term_hit@10** 是辅助指标，纯字面命中率，用来对照 soft_recall——如果 soft_recall 涨但 term_hit 跌，那说明同义词扩展真的在『跨字面』召回，是好事
> - **distinct@10** 是健康度指标，防止某次改动让 BM25 把同一条评论的 N 个 chunk 全部刷进 Top10
> - **延迟 avg / p95** 是回报率指标，确保性能代价可接受
>
> 评测要做**三档对比**（baseline / +dict / +dict+syn），不是两档。因为我预期『仅加词典』可能会有副作用（把『早餐厅』整词化后反而失去『早餐』『厅』的部分命中），需要用三档证明『词典必须搭配同义词扩展才能完整释放价值』，否则结论会被简化成『词典没用』。」

> **思考动机**：第一段是把「为什么用 soft_recall 而不是 hard_recall」交代清楚——任何指标都有偏，用之前要把偏在哪儿说出来，否则后续读这份评测的人会误以为是 hard_recall。第二段「三档对比」是我对自己假设的预防性反驳——我猜词典单独加可能会跌，那就得提前设计实验来观察这个跌；如果只跑两档（baseline vs 全开），就没法解释「为什么词典本身没明显贡献」。结果实测确实词典单独 -0.7%、叠加同义词 +21%，三档对比把这个因果关系讲清楚了。

### 收尾：commit 拆分的指令

> **Prompt #11**
>
> 「这一摊改动按职责拆 2 个 commit：
>
> 1. **配置 + 词典 + 索引模块 + 重建后的索引文件**——这是一个原子的『能力变更』，缺任何一块都不能跑
> 2. **评测脚本 + 评测结果 JSON**——这是独立的 tooling，不影响运行时；单独成 commit 后续要回滚或迁移评测都更干净
>
> 不要把它们合成一个，也不要再拆得更碎。」

> **思考动机**：commit 粒度的标准是「最小可独立回滚 / 最小可独立审查」。第 1 个 commit 里少一个文件就跑不起来，所以这五项必须在一起；评测脚本是工具链，跟运行时解耦，所以独立。这种粒度感是工程协作里最容易省略却最值钱的部分。

## 跨链路的元规则：我反复在用的几条 prompting 习惯

把上面 11 条具体指令抽掉之后，会发现我在指导 AI 编码时反复使用的几个套路：

1. **先归因，再动手**——每次新优化的第一条 prompt 都是「不要先动代码，先告诉我根因在哪」。这能避免方案在错误的归因上累积。
2. **用边界条件框定方案空间**，而不是给 AI 出方案——例如摘要 v2 我列了 4 条边界、BM25 v2 我列了 4 条「不可改动」，方案是 AI 在闭包内推出来的，不是我口述给它抄的。
3. **职责严格分离**——Map 与 Reduce 的职责、召回粒度与展示粒度、索引侧与查询侧扩展，每次涉及多组件协作时，我都会先把谁干什么、谁不能干什么钉死。
4. **要求保留兜底分支与对照实验**——v1 摘要分支保留、BM25 三档对比、配置集中化的开关，都是为「能回退、能比较」服务的，工程稳健性大于一时性能数字。
5. **commit 粒度即设计粒度**——commit 怎么拆能反映出我对「这次改了什么」是否有清晰的心理模型，所以我会主动给 AI 指 commit 拆分方案，不让它自己决定。
6. **指标先于实现**——评测脚本写之前先把每个指标的物理含义、为什么用它、它和别的指标的关系讲清楚，避免「先跑出数字再解释数字」。

这 6 条不是写给本次项目的，是我希望沉淀下来、之后任何项目都用得上的协作原则。
