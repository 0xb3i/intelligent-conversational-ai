## 一、摘要

在已集成 RAG 的全栈模板（`v1.0.0` / `v1.1.2`）基础上，我针对「检索粒度」和「生成 Prompt」做了两项独立而协同的优化：

1. **Chunking + 引用高亮**：将"整条评论 = 一个文档"细化为「句切 + 短句合并 + 长句滑窗」的 chunk 化索引；BM25 在 chunk 上召回，再按 `comment_id` 折叠为评论级结果，并在每条结果上挂 `primary_chunk` 用于前端原文高亮。
2. **Prompt v1**：把 13 条平铺要求重写为「角色 / 上下文 / 任务 / 约束 / 自校验」五段式 + 输出契约；在线接入后又针对实际渲染问题（标题僵化 + `[[ref:1,3,等]]` 病灶）迭代到 **v1.1**：自然段 + bullet 风格、动态 150-300 字、显式禁止把"等"塞进 `]]` 内部。

实测结果：
- **索引侧**：2171 条评论 → 7883 个 chunk，平均 chunk 长度由 41.6 词降至 11.6 词；Top-30 chunks 覆盖 28.99 条不同评论，命中精度提升、冗余天然抑制。
- **Prompt 侧**：v1 prompt 平均字符数 -23%（1639.6 → 1261.7）；输出契约存在率从 0% → 100%；引用违规通过 prompt 自校验 + 后端 regex 兜底降到接近 0。
- **端到端**：浏览器问答页可稳定输出"自然段 + bullet + 风险提示"三层结构，参考评论的命中句在原文上自动 `<mark>` 高亮（见图 §五）。

## 三、优化项 (2)：Chunking + 引用高亮

### 3.1 设计

- **切分策略**：以中文标点 `[。！？；…]` + 英文 `[.!?]` + 换行作为切分点；< 8 字短句合并到相邻句；> 120 字长句叠加 30 字重叠的滑窗。≤ 60 行实现，可消融。
- **数据结构**：`Chunk(chunk_id, comment_id, seq, text, char_span)`，`chunk_id = f"{comment_id}::{seq}"`。
- **检索改造**：BM25 在 `chunk_id` 维度召回 `topk × 5` 条，按 `comment_id` 折叠：同一评论保留 RRF 分最高的 chunk 作为"代表 chunk"。返回结构兼容旧版，新增 `primary_chunk = {chunk_id, text, char_start, char_end, seq}`。
- **生成端**：Prompt 中评论块改为「关键句 / 全文」两层；短评论只发关键句，长评论同时发，引用语义对齐"句"而非"评论"。
- **前端高亮**：`highlightChunkSpan(text, span)` 按字符跨度直接 `<mark>`，越界时返回原文兜底；hasChunkHit 时强制展开全文，避免折叠切断高亮。

### 3.2 离线指标（`RAG/data/evaluation/chunking_compare.json`）

| 指标 | Baseline（整条评论） | **Chunked** |
|---|---|---|
| 文档数 | 2171 | **7883**（avg 3.63 chunk/评论） |
| 平均文档长度（词） | 41.62 | **11.64** |
| 索引构建耗时 | 0.94 s | **0.56 s** |
| 词项数 | 10734 | 10764（持平，证明切分未引入词表噪声） |

| 检索对比（100 Query, Top-10） | 值 | 解读 |
|---|---|---|
| avg_overlap@10 | 4.06 | chunk 化结构性改变了召回分布，非小修小补 |
| avg_chunks_hit_per_comment(top30) | **1.04** | 每条命中评论平均只被一个 chunk 击中，命中位置精确 |
| avg_distinct_comments(top30) | **28.99** | Top-30 chunks 来自 ~30 条不同评论，多样性天然提升 |

### 3.3 真实端到端验证

调用 `POST /api/v1/chat`，问"早餐怎么样？"（节选）：

```json
{
  "_id": "680278d8e3c98b094176574b",
  "primary_chunk": {
    "chunk_id": "680278d8e3c98b094176574b::1",
    "text": "房间洗澡水大，床品很舒服睡眠很好，提供质量很好的肥皂我很喜欢，现在很多酒店都是洗手液。",
```

前端拿到 `primary_chunk` 后在原评论中对 `[48, 91)` 字符段套 `<mark>` → 用户能直接看到"为什么这条评论被召回"。

## 四、优化项 (16)：Prompt 结构化优化

### 4.1 三轮迭代

**v0**：单一 Prompt，13 条要求平铺，用户问题重复一次。问题：长输出、引用易拆成 `[[ref:1]][[ref:2]]`、闲聊会幻觉"住客评价"。

**v1.0**：五段式 + 输出契约 + 自校验。

- 角色：仅基于评论与摘要回答
- 任务：`## 直接回答 / ## 关键评价 / ## 注意事项` 三段式 ≤ 200 字
- 约束 C1–C5：引用合并 / 反幻觉 / 客观 / 简洁 / Markdown 输出
- 自校验：`[[ref:..]][[ref:..]]` 紧邻 → 合并；> 3 条 → 截断 + "等"

离线指标（`prompt_compare.json`，20 Query）：

| 指标 | v0 | **v1** | 变化 |
|---|---|---|---|
| 平均字符数 | 1639.6 | **1261.7** | **-23.0%** |
| 输出契约存在率 | 0% | **100%** | 强制结构化 |
| 自校验段存在率 | 0% | **100%** | 显著降违规 |
| 闲聊禁词约束 | 无 | **有** | 修补边界缺失 |

**v1.1（线上观测后调优）**：

实际接入浏览器后两个观察：

1. 用户反馈："## 直接回答 / ## 关键评价 / ## 注意事项 太生硬，每次都一模一样像填模板。"
2. 浏览器看到 `[[ref:1,3,等]]` 原文未被前端 [`citation-parser.ts`](../src/lib/citation-parser.ts) 识别成 badge —— 因为 regex 只接受纯数字。

针对性修法：
- Prompt 砍掉所有 H2 大标题，改为"自然段开头 → 2-3 个 bullet → 必要时一句风险提示"。
- 字数从硬约 ≤200 放宽到 150-300 自适应。
- 显式约束"等"必须在 `]]` 之外：`[[ref:1,3]]等`。
- 后端 [`sanitize_response`](../rag-service/modules/generator.py) 同步加 `_REF_ETC_INSIDE_RE` 兜底，把模型偶发的 `[[ref:1,3,等]]` 自动改写。

### 4.2 v1.1 真实输出（早餐怎么样？）

```markdown
广州花园酒店的早餐提供多种选择，种类总体丰富，中西式搭配齐全，
且部分区域供应广府特色点心 [[ref:3,8]]。

- 早餐可在多个场所享用：瀑布餐厅、顶楼旋转餐厅、桃源阁（广州特色定食）
  及30层行政楼层，桃源阁突出本地风味 [[ref:7,9]]。
- 食材与出品获较多好评，如蛋糕点心精致、现磨咖啡品质佳；也有住客认为
  口味中规中矩，缺乏鲜明广式特色 [[ref:3,5,8]]。
- 用餐时间通常至 11:00，但有反馈高峰时段需排队，且个别日期 10:30 即
  开始撤餐 [[ref:10]]。

需要留意的是，部分客人反映早餐高峰期等位较久，且 11:00 截止时间
存在提前收档情况 [[ref:10]]。
```

字数 240，引用全部合规，结构自然。

### 5.3 关键 Bug 修复（在线接入过程中产生）

| Bug | 根因 | 修法 |
|---|---|---|
| `TypeError: ref.images.map is not a function` | 本地 CSV 模式下 `images` 是 JSON 字符串而非数组 | [`qa.ts mapToComment`](../src/lib/qa.ts) 兼容数组/字符串两种形态 |
| 启动卡在 `Waiting for application startup` | `get_all_comments_from_insforge` 无凭证阻塞 | [`utils/database.py::load_comments`](../rag-service/utils/database.py) 加 `timeout=8` + 本地 CSV 回退 |
| `got multiple values for keyword argument 'enable_hyde'` | `main.py` 同时硬编码 + 透传 `options` | [`main.py`](../rag-service/main.py) 用 `setdefault` 合并 |
| 高亮在问答页不生效 | `ChatMessage.tsx` 走自己的卡片渲染，没用 `CommentCard.highlightChunkSpan` | [`ChatMessage.tsx`](../src/components/qa/ChatMessage.tsx) 同步引入该函数 |
| `[[ref:1,3,等]]` 未渲染成 badge | "等"塞进了 `]]` 内部 | Prompt 显式禁止 + sanitize 正则兜底 |

## 六、评估方法与不足

### 6.1 评估方法

- 离线代理指标：BM25 召回结构变化（`chunking_compare.json`）；Prompt 长度 / 输出契约存在率（`prompt_compare.json`）
- 在线 Smoke：固定 6 个预设问题 + 1 个长问题，肉眼复核引用合规率、结构稳定度、高亮命中位置
- 单元测试：`sanitize_response` 三类违规对照样本

### 6.2 不足

- 未引入 LLM 评估器（如 RAGAS）做"答案质量"打分；课程 DDL 时间预算不足。
- 摘要库 / 反向 Query 库未跟随切分（设计上保持聚合粒度，但 `chunk_id ↔ comment_id` 反查表的工程化扩展仍待补）。
- 主题切分（基于 `categories.json` 的策略 C）未交付，需要类别小模型/聚类，与优化项 (3)/(4) 强耦合。
